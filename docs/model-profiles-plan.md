# DigUp: хранение модели, выбор папки, удаление и скорость индексации

**Статус:** Phase 0–2 (хранение модели, импорт/проверка/удаление и смена папки) **сделаны и проверены 2026-10-25**.
Скоростная часть (Phase 3: пул процессов и параллельная подготовка) тоже **сделана 2026-10-25**; GPU-батчинг после
замеров отклонён (Phase 4); Phase 5 — только после появления второй модели. Это план реализации, а не отчёт о
сделанном; сделанное отмечено явно.
**Обновлено:** 2026-10-25, после замеров `docs/image-embedding-performance.md` и живой проверки Storage.
**Проверено 2026-10-25:** Rust-тесты shell — 52/52; Swift — 128 тестов, единственный сбой
`modelFilesComeFromTheHuggingFaceCacheWhenThere` — среда без права создавать symlink (Win32 1314), не регрессия.
Живой запуск шелла: старая папка `%LOCALAPPDATA%\DigUp\Models` используется на месте; Move A → B копирует через
`.partial`, проверяет SHA-256, переключает поиск и удаляет старые файлы только после готовности B; Use C не копирует;
`Check Files` проходит; удаление освобождает папку, ставит `modelRemoved`, а следующий запуск не скачивает модель и
работает в keyword-режиме; чужой `modelsVolume` даёт `unavailable` без скачивания.
**Платформа первого этапа:** Windows 10/11; macOS/Linux — после Windows.
**Область:** одна активная модель (EmbeddingGemma 2 Q8_0), папка модели на SSD, импорт/проверка/удаление файлов,
безопасное переключение папки; скорость индексации — пул процессов-эмбеддеров и параллельная подготовка
(батчинг изображений/текста отклонён замерами, раздел 3).

> **Главное решение:** альтернативные модели сейчас **не добавляем**. EmbeddingGemma 2 остаётся единственным профилем: Apache 2.0, текст + изображения + видео + аудио, upstream llama.cpp, 768d. Но путь к файлам, манифест, проверка и удаление оформляются так, чтобы второй профиль можно было добавить без переделки хранилища. Индекс пока остаётся один: смена папки модели не меняет векторы и не должна вызывать переиндексацию.
>
> **Скорость** решена не батчингом, а пулом независимых процессов и параллельной подготовкой батчей: 1.56× на
> полном наборе (4306 изображений), векторы бит-в-бит. Батчинг `mtmd` измерен и отклонён (раздел 3).

## 1. Что проверено в коде и API (без предположений)

### 1.1. Текущее хранение и запуск

- `Sources/DigUpKit/ModelFiles.swift` — единственный источник имён, размеров, SHA-256, репозитория и ревизии. Сейчас два файла:
  - `embeddinggemma-2-Q8_0.gguf` — 309 855 456 байт;
  - `mmproj-embeddinggemma-2-Q8_0.gguf` — 554 821 024 байта.
- `Sources/LlamaRuntime/LlamaModels.swift`:
  - `DIGUP_MODELS` задан → helper смотрит **только** в эту папку;
  - переменная не задана → `ModelFiles.installed` (Application Support), затем Hugging Face cache;
  - `locate()` проверяет только наличие файлов, не размер и не хеш;
  - `complete` также проверяет только наличие.
- `Sources/digup/DownloadModel.swift`:
  - `download-model --to DIR` создаёт папку, копирует/качает отсутствующие файлы, проверяет SHA-256 перед присвоением финального имени;
  - `ModelFiles.missing(in:)` считает файл отсутствующим **только по имени**; файл с правильным именем и неверным размером считается готовым;
  - при скачивании поверх существующего файла с тем же именем `moveItem(partial, final)` на Windows может не заменить файл;
  - проверки свободного места нет.
- `shell/src-tauri/src/main.rs`:
  - `options.models` (`--models`) — единственный способ задать папку из shell;
  - `download_launch()` передаёт `--to` только при `options.models`; иначе helper пишет в `%LOCALAPPDATA%\DigUp\Models`;
  - `helper_env()` задаёт `DIGUP_MODELS` только при `options.models`;
  - `storage()` показывает `options.models` или `%LOCALAPPDATA%\DigUp\Models`;
  - поисковый helper создаётся один раз в `setup()` с зафиксированным `Launch`; после `search.stop()` он стартует с **тем же** env. Значит, смена папки модели и `set_processor_only` без доработки не подействуют на уже созданный `SearchService`;
  - `measure_then_index()` задаёт `DIGUP_MODELS` только при `options.models` и не передаёт `DIGUP_DEVICE`;
  - `ModelDownload` один; отдельного задания для скачивания в новую папку нет;
  - при каждом старте безусловно запускается `download-model`. После осознанного удаления модели это снова скачало бы её.
- `shell/src-tauri/src/helper.rs`:
  - `SearchService::stop()` ждёт до 2 с, затем kill;
  - `IndexService::stop()` так же;
  - `ModelDownload::stop()` убивает процесс и ждёт;
  - `SearchService` не имеет метода смены `Launch`.
- `shell/src-tauri/src/settings.rs` — `serde(default, rename_all = "camelCase")`; новые поля можно добавлять без миграции JSON.
- `Sources/LlamaRuntime/LlamaEmbedder.swift`:
  - `embedImages` и `embedAudio` вызывают `embedMedia` через `map`, то есть **по одному файлу**;
  - `embedTexts` уже батчится: до 16 последовательностей и 2048 токенов на `llama_process`;
  - `n_ctx = n_batch = n_ubatch = 2048`, `n_seq_max = 16`;
  - `mtmd_context_params_default()` используется без изменения `batch_max_tokens` (по умолчанию 1024);
  - аудио обрезается до 30 с, 30-секундное окно даёт около 750 строк эмбеддингов.
- `Sources/DigUpKit/Indexer.swift`:
  - изображения и скриншоты идут в модель по 8;
  - кадры видео передаются все сразу в `embedImages`, звуковые окна — все сразу в `embedAudio`;
  - подготовка следующего задания уже идёт на отдельном потоке, пока модель считает текущее; с 2026-10-25
    картинок готовится вперёд столько батчей, сколько воркеров пула (`Indexer.prepareAhead`).
- `Sources/DigUpKit/Vectors.swift` — размерность 768 зашита в `VectorStorage`, `Searcher`, `Vectors.half`; менять её сейчас не нужно.

### 1.2. Что реально умеет mtmd в запиненном llama.cpp b11461

Проверено по `Vendor/llama.cpp/tools/mtmd/`:

- `mtmd_batch_init`, `mtmd_batch_add_chunk`, `mtmd_batch_encode`, `mtmd_batch_get_output_embd` есть в `mtmd.h`.
- `mtmd_batch_add_chunk` возвращает:
  - `0` — добавлено;
  - `1` — общая ошибка;
  - `2` — батч переполнен (по `batch_max_tokens`) или батчинг вообще не поддерживается;
  - `3` — чанк несовместим с уже лежащими.
- Изображения можно батчить, только если совпадают `nx`, `ny` и тип позиций (`mtmd_image_tokens::can_batch_with`). То есть один батч — это изображения **одинаковой сетки токенов**, а не просто одинакового бюджета.
- `clip_graph_gemma4v` (наш визуальный энкодер) переопределяет `support_batch() == true`; `clip_encode()` умеет обрабатывать несколько изображений одной графой.
- `clip_graph_gemma4a` (аудиоэнкодер) **не** переопределяет `support_batch`; базовый `clip_graph::support_batch()` возвращает `false`. В `mtmd_input_chunk::can_batch_with` стоит `// TODO: allow batching audio chunks of the same size` и `return false` для аудио.
  **Следствие:** батчить аудиоэнкодер сейчас нельзя. Нельзя и «объединить два 30-секундных окна в один вход» — это изменит векторы.
- `mtmd_batch_encode` копирует `batch_f32` всех чанков в первый и вызывает один encode. Выход лежит подряд, `mtmd_batch_get_output_embd` выдаёт указатель на начало строк конкретного чанка.
- `batch_max_tokens` по умолчанию 1024; первый чанк добавляется даже если он больше лимита.
- `mtmd_helper_bitmap_init_from_file` / `_from_buf` в `mtmd-helper.h` явно помечены **thread-safe**. `mtmd_tokenize` такой гарантии не даёт; его нельзя вызывать параллельно с тем же `mtmd_context`.
- `mtmd_batch` не владеет чанками: чанки должны жить до конца `mtmd_batch_encode`.

## 2. Целевая архитектура

### 2.1. Одна активная модель, настраиваемая папка

Настройки получают три поля:

```rust
pub struct Settings {
    // ... существующие поля ...

    /// Папка, в которой лежат оба файла модели. None: папка по умолчанию.
    pub models_folder: Option<String>,
    /// Серийный номер тома, на котором выбрана папка (Windows), или st_dev (Unix).
    /// Нужен, чтобы не писать модель на чужой диск с той же буквой после переподключения.
    pub models_volume: Option<u64>,
    /// Модель удалена пользователем: при старте не скачивать её автоматически.
    pub model_removed: bool,
    /// Старая папка после Move: её файлы удаляются только после первого `ready` новой модели.
    pub model_cleanup: Option<String>,
}
```

`models_folder` хранит **фактическую папку с двумя GGUF**, а не «корень всех моделей». Это убирает неоднозначность «папка профиля против папки-контейнера» и позволяет позже хранить путь в записи профиля.

Приоритет пути:

1. `--models DIR` (dev/совместимость) — ровно `DIR`, без добавления подпапок.
2. `settings.models_folder`, если задан.
3. Если настройки нет:
   - `%LOCALAPPDATA%\DigUp\Models` (старое место), если там есть **хотя бы один** из файлов модели — использовать его как есть, ничего не перемещать;
   - иначе `%LOCALAPPDATA%\DigUp\Models\embeddinggemma-2`.
4. Linux аналогично: `$XDG_DATA_HOME/digup` или `~/.local/share/digup`; macOS-шелл не затрагиваем, у Mac-приложения свой `modelsDirectory`.

Правило «хотя бы один файл» важно: нельзя собрать модель из двух папок. Если в старом месте лежит только текстовая часть, helper должен докачать вторую туда же, а не искать mmproj в новой папке.

Для этой машины целевой путь:

```
G:\Ai\DigUp\Models\embeddinggemma-2\
  embeddinggemma-2-Q8_0.gguf
  mmproj-embeddinggemma-2-Q8_0.gguf
```

`G:\Ai\DigUp\Models` — папка-контейнер, которую выбирает пользователь; приложение создаёт в ней `embeddinggemma-2` и показывает конечный путь в UI. Если пользователь выберет уже существующую папку с файлами, она используется напрямую.

### 2.2. Единая точка вычисления пути

Новый модуль `shell/src-tauri/src/models.rs` (или функции в `options.rs`, если модуль кажется лишним) с чистыми функциями:

```rust
pub const MODEL_FILES: [&str; 2] = [
    "embeddinggemma-2-Q8_0.gguf",
    "mmproj-embeddinggemma-2-Q8_0.gguf",
];
pub const PROFILE_ID: &str = "embeddinggemma-2";

pub fn default_models_folder() -> PathBuf;
pub fn legacy_models_folder() -> PathBuf;
pub fn resolve_models_folder(options: &Options, settings: &Settings) -> PathBuf;
pub fn volume_id(folder: &Path) -> Option<u64>;
pub fn folder_state(folder: &Path, expected_volume: Option<u64>) -> FolderState;
```

`FolderState`: `Available`, `Missing` (родитель есть, папки нет), `Unavailable` (корень тома не существует), `WrongVolume` (том другой), `NotFolder`.

`Shell::models_folder()` вызывает `resolve_models_folder`. Все места, которые сейчас читают `options.models` напрямую, переводятся на него:

- `download_launch()`;
- `helper_env()`;
- стартовый `Launch` для `search-service`;
- `measure_then_index()`;
- `storage()`;
- новые команды смены/удаления.

`helper_env()` **всегда** кладёт `DIGUP_MODELS` в env (кроме случая, когда путь не нужен вообще), а не только при `options.models`.

### 2.3. Исправление жизненного цикла helper'ов

Без этого смена папки будет «сохраняться, но не применяться».

1. `SearchService` получает:
   ```rust
   pub fn set_launch(&self, launch: Launch)
   ```
   Внутри — `Mutex<Launch>`; `send()` клонирует актуальный `Launch`. `set_launch` останавливает текущий процесс, чтобы следующий запрос стартовал с новым env.
2. `Shell` хранит `search` как есть; `set_launch` вызывается после смены папки модели и в `set_processor_only`.
3. `measure_then_index()` собирает env через `shell.helper_env()` и передаёт его `Command`; `--models` больше не единственный источник.
4. Стартовый `search-service` в `setup()` получает env, вычисленный из `options` + `settings` до создания `Shell`.
5. `stop_helpers()` получает вариант `stop_helpers_for_model_change()`: останавливает `model`, `transfer`, `search`, `index`; ждёт окончания `measuring`/`estimating` или отказывает команде с понятным сообщением.
6. Speed-check: если он запущен, команда смены/удаления возвращает `"идёт проверка скорости, попробуйте через несколько секунд"`; UI держит кнопку выключенной по `state.measuring`. Не убиваем дочерний процесс speed-check, чтобы не оставить его собственный CPU-замер.

### 2.4. Состояния модели

Сейчас `model_state` — только `checking|downloading|waiting|ready|failed`. Добавляем различимые состояния:

```json
{"state":"missing","message":"Model files are not installed"}
{"state":"unavailable","message":"The model folder is unavailable: G:\\Ai\\DigUp\\Models"}
{"state":"verifying","folder":"...","checked":1,"total":2}
{"state":"downloading","folder":"...","bytes":0,"total":864676480}
{"state":"ready","folder":"..."}
{"state":"failed","message":"..."}
```

`model_ready()` по-прежнему `state == "ready"`. `may_index()` не запускает индексацию при `missing/unavailable/failed`.

При старте:

1. `models_folder()` даёт путь.
2. `folder_state`:
   - `Unavailable/WrongVolume` → `unavailable`, **не** создавать папку, **не** запускать download;
   - `Missing` и `model_removed == false` → создать и запустить download;
   - `Missing` и `model_removed == true` → `missing`, ничего не качать;
   - `Available` → быстрая проверка размеров; если оба файла есть и размеры верны → `ready`; если чего-то нет/размер неверен и `model_removed == false` → download; если `model_removed == true` и файлов нет → `missing`.
3. Если `model_removed == true`, но оба файла внезапно на месте и размеры верны — снять флаг и считать `ready` (пользователь скопировал файлы вручную).

### 2.5. Манифест, проверка, импорт и удаление: новые команды helper'а

Хеши и размеры в Rust не дублируются: они приходят из манифеста helper'а. Имена двух файлов — стабильный контракт и продублированы в Rust только для выбора старой папки при первом запуске; при смене профиля этот список меняется вместе с `ModelFiles`. Добавляем в `digup` команды без загрузки модели:

```text
digup model-manifest --json
  {"files":[{"name":..., "bytes":..., "sha256":..., "url":...}], "total":...}

digup model-verify --to DIR --json
  {"event":"file","name":...,"bytes":...,"present":true,"ok":true,"problem":null}
  {"event":"done","ok":true,"folder":"..."}

digup model-import --to DIR FILE... --json
  копирует выбранные файлы в DIR через .partial, проверяет размер и SHA-256,
  затем атомарно переименовывает; файлы не из манифеста отвергает.

digup download-model --to DIR [--check]
  --check: проверить и существующие файлы по размеру и SHA-256, а не только по наличию.
```

Реализация:

- `ModelFiles` получает:
  - `missing(in:)` — отсутствует **или размер не равен** ожидаемому;
  - `complete(in:)` — оба файла есть и размеры верны;
  - `verify(in:)` — размер + SHA-256 для каждого;
  - `manifestJSON`.
- `DownloadModel`:
  - проверяет свободное место (`missing + 200 МБ`) до скачивания;
  - при замене существующего финального файла сначала проверяет `.partial`, затем удаляет старый финальный файл и переименовывает новый (окно без файла допустимо: `.partial` останется для продолжения);
  - `--check` перепроверяет и перекачивает повреждённые файлы.
- `model-import` копирует, а не «усыновляет» файлы из разных папок. Если оба выбранных файла уже лежат в целевой папке, копирование не нужно — shell просто вызывает `model-verify`.
- Свободное место в shell: `GetDiskFreeSpaceExW` на Windows и `statvfs` через уже подключённый `libc` на Unix; новых зависимостей нет.

Имена из `model-manifest` перед удалением проверяются: только basename, без `/`, `\`, `..`; удаляются только два известных имени и их `.partial`. Никакого рекурсивного удаления папки.

### 2.6. Смена папки модели: транзакционный сценарий

Новая команда `model_folder_plan(target)` (быстрая, без хеширования) возвращает:

```json
{"kind":"use" | "download" | "move" | "invalid",
 "target":"...", "files":[{"name":...,"bytes":...}],
 "free":123456789, "problem":null}
```

Правила:

- `target` — абсолютный путь; кириллица, пробелы и длинные пути допустимы;
- если том недоступен — `invalid`; для новой папки её серийный номер записывается при активации, а не сравнивается со старым `models_volume`; сравнение с сохранённым номером делается только для **текущей** папки при старте;
- если оба файла есть и размеры верны — `use`; SHA-256 проверяется в фоне перед подтверждением;
- если папка пуста/частична — `download` (если места хватает); если текущая модель полная, для пустой папки предлагаются оба варианта, `move` — по умолчанию, `download` — если пользователь хочет оставить старую копию;
- если в папке есть посторонние файлы — они не трогаются; модель может лежать рядом с ними.

Команда `model_folder_apply(target, action)`:

1. Ставит `models_busy`, проверяет, что нет `measuring`.
2. Для `download`: запускает отдельный `transfer`-job `download-model --to target`; текущая модель и индексация продолжают работать. По `done` — `model-verify`.
3. Для `move`: копирует текущие два файла в `target` через `.partial`, проверяет SHA-256; текущая модель работает.
4. Для `use`: только `model-verify` (в фоне, с прогрессом).
5. После успешной проверки — `activate`:
   - `transfer.stop()`;
   - `search.stop()`, `index.stop()`, `model.stop()`;
   - сохранить `models_folder`, `models_volume`, `model_removed = false`;
   - `search.set_launch(launch_with_new_env())`;
   - `model_state = checking`, запустить `download-model --to` (быстрая проверка), затем `measure_then_index`;
   - `run_index` после готовности модели.
6. Для `move` старый источник **не удаляется сразу**. В настройку `model_cleanup` пишется старая папка. Когда новая модель впервые станет `ready`, удаляются только два файла манифеста и `.partial` из старой папки; при ошибке (файл занят) запись остаётся и повторяется на следующем старте. UI показывает «Старые файлы остались: … (865 МБ)» и кнопку удаления.
7. При любой ошибке до `activate` настройка не меняется; текущая модель продолжает работать.

`models_busy` — `Mutex<()>`/`AtomicBool`, одна операция за раз. Кнопки в UI блокируются на время.

### 2.7. Удаление файлов модели

Команда `delete_model_files` (UI сначала показывает подтверждение):

1. Если `models_busy` — отказ.
2. Если `measuring` — отказ с сообщением.
3. `transfer.stop()`, `model.stop()`, `search.stop()`, `index.stop()`.
4. Взять имена из `MODEL_FILES` (они же — контракт `ModelFiles`), проверить, что это basename без `..`/разделителей; `model-manifest` нужен только для размеров и проверки, не для удаления.
5. Удаление каждого файла и `.partial` с повтором 20 × 250 мс (Windows может держать mmap недолго после выхода процесса).
6. Если все удалены:
   - `model_removed = true`;
   - `model_state = missing`;
   - `run_index` не запускается;
   - поиск остаётся доступным в keyword-режиме (search helper без модели отвечает на текстовые запросы, но не строит векторы).
7. Если хоть один файл не удалён — `model_removed` не ставится; возвращается имя файла и причина. UI не пишет «удалено».
8. Опция «удалить индекс» в первом срезе **не** предлагается: удаление индекса — отдельное разрушительное действие, не нужное для освобождения 865 МБ. Индекс остаётся, повторная установка модели продолжит работу без переиндексации.

После удаления в Storage:

```
EmbeddingGemma 2 · Google · Apache 2.0 · 865 MB
Status: Not installed
Location: G:\Ai\DigUp\Models\embeddinggemma-2
[Download Model…]
```

Автоскачивание при следующем старте не происходит из-за `model_removed`. Кнопка Download сбрасывает флаг и запускает `download-model --to`.

### 2.8. Импорт локальных файлов

UI Storage → «Use Model Files…»:

- нативный выбор файлов (multi-select);
- если оба выбранных файла лежат в одной папке:
  - `model-verify --to <эта папка>`;
  - при успехе — `use` (папка становится текущей, ничего не копируется);
- если файлы в разных папках:
  - `model-import --to <текущая папка модели> <file1> <file2>`;
  - helper копирует через `.partial`, проверяет SHA-256, заменяет;
- если не хватает места — ошибка до копирования;
- «Copy Links» копирует две ссылки из `model-manifest` (для сетей, где Hugging Face недоступен);
- «Export» в первый срез не входит.

### 2.10. Проверка тома

`models_volume`:

- Windows: `GetVolumePathNameW` + `GetVolumeInformationW` (серийный номер тома) для ближайшего существующего родителя; `windows-sys` уже включает `Win32_Storage_FileSystem`.
- Unix: `MetadataExt::dev()` ближайшего существующего родителя.
- Если `models_volume` задан и текущий том другой → `WrongVolume`; download/delete/switch запрещены, UI говорит «This folder is on a different disk than when it was chosen».
- Если `models_volume` не задан (старые настройки), при первом успешном использовании он записывается.
- Сравнение путей на Windows — без учёта регистра, с нормализацией `/` → `\` и без завершающего разделителя. Не используем `canonicalize`: он падает для отсутствующей папки и добавляет `\\?\`.

Это защищает от типичного сценария: внешний SSD `G:` отключён, буква `G:` занята флешкой, приложение не должно скачать 865 МБ на неё.

### 2.11. Конкурентность и блокировки

- Все операции с папкой модели — через один `models_busy`; параллельный `model_folder_apply`, `delete_model_files`, `set_processor_only` получает отказ.
- `SearchService::set_launch` обязателен; без него новый env не дойдёт до поиска.
- `IndexService` получает `Launch` на каждый запуск, поэтому подхватывает новый env сам.
- Перед удалением/переключением ждём `measuring == false`; `estimating` не держит модель, но может замедлить проверку, его ждать не обязательно.
- `transfer` — отдельный процесс; его нельзя смешивать с `ModelDownload`, иначе прогресс и `done` попадут в состояние активной модели.
- На Windows удаление после `stop()` может ещё несколько сотен миллисекунд упираться в mmap; retry-цикл обязателен.
- `model_removed` и `models_folder` сохраняются одной атомарной записью `Settings::save` (уже пишет через `.json.new` + rename).

## 3. Скорость индексации: пул процессов вместо GPU-батчинга

### 3.1. Решение после замеров 2026-10-25

Черновик этого плана предполагал батчинг изображений в `mtmd_batch`. Он измерен и **отклонён**:

- бюджет 280 (скриншоты): батч 8 — на 9% **медленнее** одиночного пути;
- бюджет 140 (фото): на 11.5% быстрее, но векторы дрейфуют (cosine min 0.99938);
- `mtmd_image_tokens_get_nx/ny` для gemma4v возвращает `(n_tokens, 1)`, поэтому группировка по
  `mtmd_batch_add_chunk` склеивает портрет с альбомным кадром и роняет cosine до 0.64;
- текстовый батчинг даёт 5–12% и тоже меняет векторы (cosine 0.99989–0.99995).

Полные замеры, скрипты и сырые данные — `docs/image-embedding-performance.md`.

Вместо этого принят **пул независимых процессов `digup worker`** (каждый со своим llama.cpp context)
и **параллельная подготовка** батчей в `Indexer`:

- 1 процесс загружает RTX 4070 Ti SUPER на 32% (1.9 ГБ VRAM); 4 процесса — 87–89% (6.1 ГБ);
- реальная папка, 4306 изображений, настоящий `index-service`: 197.35 с одним воркером → 126.88 с
  четырьмя, **1.56×**; 44.4 → 27.7 мс на изображение;
- векторы **бит-в-бит** совпадают с одним воркером (4306/4306, cosine 1.0): переиндексация не нужна,
  `vectorVersion` не меняется;
- 5 воркеров дают ещё ~6% при заметно большем VRAM — предел 4.

### 3.2. Что уже сделано (2026-10-25)

- `Sources/digup/WorkerPool.swift` — пул: воркеры стартуют параллельно, запросы делятся между ними
  (текст идёт через первый), `close()` закрывает все одновременно.
- `Sources/DigUpKit/Indexer.swift` — `prepareAhead`: подготовка картинок идёт на конкурентной очереди,
  впереди держится столько батчей, сколько воркеров; остальные виды — один батч, как раньше.
  `nowReading` стал набором чтений с токенами для watchdog (при параллельном чтении он берёт самое давнее).
- `Sources/LlamaRuntime/LlamaEmbedder.swift` — `gpuMemory` (свободная память дискретной карты);
  батчинг откатан.
- `Sources/digup/main.swift` — `DIGUP_INDEX_WORKERS=<n>|auto`: `auto` даёт 1–4 воркера по свободной VRAM
  (2 ГБ на воркер, не больше половины логических CPU); при сбое пула — откат на один процесс.
- `shell/src-tauri/src/main.rs` — индексатору ставится `DIGUP_INDEX_WORKERS=auto`; ручное значение сильнее.

### 3.3. Что остаётся последовательным и почему

- **Аудиоэнкодер** (`clip_graph_gemma4a`) upstream батчинг не поддерживает; патчить его не нужно:
  аудиоокна распределяются по процессам пула, каждый считает своё окно.
- **Текст** (`embedTexts`) идёт через первый воркер: это 8–10% времени индексации, а дробление
  текстовых батчей между процессами изменило бы векторы. Для текстовых папок пул не даёт ускорения,
  но и не мешает: при `auto` на интегрированной графике/CPU он не включается.
- **PDF-текст** и документы остаются на первом воркере по той же причине.

### 3.4. Пределы и деградация

- `DIGUP_DEVICE=cpu`, интегрированная графика и macOS/Metal: `auto` даёт 1 воркер (в процессе),
  пул не включается.
- Если воркеры не стартуют (нет VRAM, сбой драйвера), `makeIndexEmbedder` пишет причину в stderr
  и откатывается на один процесс: индексация продолжается, только медленнее.
- Память: при выборе числа воркеров — 2 ГБ на воркер; фактически 1 воркер — 1.9 ГБ, 4 — 6.1 ГБ.
- Четыре модели грузятся параллельно, ~4.5 с один раз за жизнь хелпера. Для одиночного нового файла
  это заметно; ленивый старт воркеров — кандидат на потом, в текущем срезе его нет.
- Папка модели на внешнем/медленном диске: каждый воркер читает оба GGUF при старте (4 × 865 МБ). Если это
  станет заметно, для таких папок стоит ограничить `auto` двумя воркерами или дать настройку; сейчас диск не
  различаем.

### 3.5. Критерии

- Изображения на CUDA: throughput в конвейере не ниже 1.5× baseline, GPU utilization выше.
  Уже измерено: 1.56× на полном наборе.
- Векторы бит-в-бит с одиночным воркером; `ReferenceVectorTests` без изменений; `vectorVersion` не меняется.
- CPU: не медленнее baseline (пул не включается).
- OOM нет; при нехватке VRAM — меньше воркеров или один процесс.

## 4. Поэтапный план

### Phase 0 — защитные тесты и базовая линия

1. Baseline скорости **снят 2026-10-25**: 200 файлов и полный набор 4306 изображений, 1 против 4 воркеров,

| Чистая установка | Папка по умолчанию создаётся, download идёт, модель `ready` |

## 6. Риски и меры

| Риск | Мера |
|---|---|
| Пул меняет векторы | Замерено бит-в-бит (4306/4306); при расхождении — не включать |
| OOM на 8 ГБ | `auto` по свободной VRAM (2 ГБ/воркер, ≤4), откат на один процесс |
| Четыре модели не стартуют | Откат на один процесс, причина в stderr; индексация продолжается |
| Аудио нельзя батчить | Клип не патчим; окна распределяются по процессам пула |
| Смена папки не доходит до поиска | `SearchService::set_launch` + тест env |
| Удаление при открытом mmap | `stop()` + retry; ошибка без ложного успеха |
| Автоскачивание после удаления | `model_removed`, проверяется на старте |
| Чужой диск с той же буквой | `models_volume` |
| Потеря старой модели при Move | Старые файлы удаляются только после `ready` новой; `model_cleanup` |
| Посторонние файлы в папке | Удаляются только имена из манифеста и `.partial` |
| Свободное место | Проверка до download/import; понятная ошибка |
| CPU-регрессия | На CPU пул не включается (`auto` → 1) |
| Metal/iGPU не измерялись | `auto` не включается: один воркер в процессе |

## 7. Критерии приёмки

1. На этой машине активная папка — `G:\Ai\DigUp\Models\embeddinggemma-2`; файлы используются на месте, вторая копия в `%LOCALAPPDATA%` не создаётся.
2. `Delete Model Files…` удаляет только два файла модели и `.partial`, освобождает 865 МБ, после перезапуска модель не скачивается сама.
3. Отключение G: даёт понятное `unavailable`, не скачивает модель в другое место.
4. `Check Files` проверяет размер и SHA-256 и показывает повреждённый файл.
5. Импорт из одной папки не копирует; импорт из разных папок копирует и проверяет.
6. Смена папки не вызывает переиндексацию; fingerprint и векторы не меняются.
7. Изображения на CUDA: ≥1.5× быстрее baseline (замерено 1.56× на 4306); GPU загружен заметно выше; на CPU не медленнее.
8. Аудио: окна идут через пул, энкодер последователен; векторы совпадают.
9. `ReferenceVectorTests` проходит без повышения `vectorVersion`; векторы пула бит-в-бит.
10. Все существующие тесты, включая `DigUpKitTests`, `LlamaRuntimeTests` и Rust-тесты shell, проходят.
